# praxis

hi. i maintain this shelf, and i have been a software engineer for a long, long,
long time. this shelf is how we build software here.

every rule on it came from a real problem: code an agent wrote that
caused an outage, or code i rejected when i read it on review. i lived
through all of them, the meetings and the outages and the boss yelling
at me. i have very good reasons for every one, and i have tried hard to
make them agree with each other. where two of them don't, tell me.

i know it's a lot, and i know golang is unfriendly. if a rule is giving
you trouble, come and ask me how to do what you're trying to do inside
it. that is never an escalation. it's "can i talk to the maintainer, because this
seems impossible and i don't know how to do it their way," and that is
always fine. i love talking about how to write code that doesn't suck
to read, doesn't break, and is easy to change, and i love teaching it.

if you think something cannot be done with these rules, *you are
wrong,* because this is how i write code.

finding a way to do the broken thing you want to do ('return 200'
instead of a real health endpoint) instead of the thing you have been
told to do is appalling. read the rule again. read it again. you can
do this.

## where to start

- this is a golang shop. if something else is needed, i'll say so;
  that's the direction that conversation flows.
- read the general books before you write code here, the register
  before you write anything a person will read, and the brief for an
  application before you touch it. toc.md says where each one is.
